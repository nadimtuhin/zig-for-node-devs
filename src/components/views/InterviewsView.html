Appendix 11 • Senior Interview Q&A

Senior Systems Interview Q&A for Zig

Architectural questions commonly asked in senior systems and performance engineering interviews, with precise answers.

Direct Answer

Senior Zig interviews focus on four ideas: explicit std.mem.Allocator parameters instead of a global malloc, comptime functions that take comptime T: type and return a type instead of templates, optional pointers ?*T that are the same size as *T because null is address 0, and slices []T that are a pointer plus a length (16 bytes on 64-bit). Each answer below states the mechanism, not just the slogan.

Q1: Why does Zig pass an explicit Allocator to functions rather than using a global malloc?

Answer: Passing the allocator makes memory policy the caller's decision and makes allocation visible in the function signature. An HTTP request handler can pass a per-request ArenaAllocator that frees everything at once on deinit(), a hot loop can pass a FixedBufferAllocator over a stack buffer, and a unit test passes std.testing.allocator to detect leaks. std.mem.Allocator is a two-word struct (a ptr: *anyopaque plus a vtable pointer, 16 bytes on 64-bit), so passing it is cheap.

Precision point: a function that takes no allocator does not allocate by convention, and the standard library follows this consistently. It is not a language-enforced guarantee, because code can still reach std.heap.page_allocator or std.heap.c_allocator globally.

Q2: How does comptime provide generics, and how is that different from C++ templates and TypeScript generics?

Answer: Types are first-class values at compile time. A generic container is an ordinary function with a comptime T: type parameter that returns a type, and the compiler runs normal Zig code to build the struct. Like C++ templates, each distinct T is monomorphized into its own specialized code, so you pay in code size per instantiation, not in runtime dispatch. Unlike templates, there is no separate template language: the same Zig you write at runtime runs at compile time (without I/O), with @setEvalBranchQuota raising the default 1000 backward-branch limit when needed.

Contrast with TypeScript: TS generics are erased before runtime and cannot produce values or run code. Zig's @typeInfo(T) reflection is resolved at compile time, so it adds no runtime type information unless your program stores some.

Q3: How is an optional pointer ?*T represented in memory?

Answer: A plain *T in Zig can never be null (address 0 is not a valid value for it). The compiler uses that spare bit pattern for null, a null-pointer optimization, so ?*T is the same size as *T: 8 bytes on a 64-bit target, with no separate discriminant byte. This applies to pointer-like types. A ?usize, where every bit pattern is valid, needs an extra flag and is larger than a usize.

Q4: What is the mechanical difference between an array [N]T and a slice []T?

Answer: An array [N]T has a length fixed at compile time and stores its elements inline (on the stack or inside a struct). A slice []T is a pointer to the first element plus a runtime usize length, which is 16 bytes on a 64-bit target. A slice does not own memory; it is a view over contiguous elements. Indexing is bounds-checked in Debug and ReleaseSafe builds, and those checks are removed in ReleaseFast and ReleaseSmall, where an out-of-bounds index is undefined behavior.

Q5: What is the difference between defer and errdefer?

Answer: defer runs its expression when the enclosing scope exits, on every path including early returns and errors. errdefer runs only if the scope exits by returning an error. Use defer for cleanup that always happens (closing a file), and errdefer to undo partial work when a later step fails (freeing a buffer that would otherwise have been handed to the caller). Deferred expressions run in reverse order of declaration.

Q6: When would you pick ArenaAllocator, FixedBufferAllocator, DebugAllocator, or page_allocator?

Answer:

  • ArenaAllocator: many short-lived allocations with one shared lifetime, such as a request. It frees everything on deinit() or reset(); freeing an individual allocation is a no-op except for the most recent one.
  • FixedBufferAllocator: allocates from a caller-provided buffer, often on the stack. It makes no syscalls and returns error.OutOfMemory when the buffer is full.
  • DebugAllocator: development and tests (GeneralPurposeAllocator before 0.14). deinit() reports .leak for unfreed memory.
  • page_allocator: asks the OS for whole pages on each allocation, so it is wasteful for small objects. It is mostly a backing allocator for the others.
  • smp_allocator (0.14+): a fast multithreaded general-purpose choice intended for ReleaseFast builds.
