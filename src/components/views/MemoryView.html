Appendix 02 • Systems Memory

The Allocator Architecture

No hidden malloc and no garbage collector, so no GC pauses: every allocation goes through an explicit allocator you pass in.

Direct Answer

Node.js allocates every object on the V8 heap and reclaims it with a generational garbage collector (a semi-space Scavenger for new space, Mark-Sweep-Compact for old space). Zig has no garbage collector: any function that allocates takes an explicit std.mem.Allocator (DebugAllocator, ArenaAllocator, FixedBufferAllocator, page_allocator, c_allocator or, in 0.14, smp_allocator). You free with defer or by resetting an arena, so there are no GC pauses, but leaks and use-after-free become your responsibility.

Node.js / V8

How does Node.js manage memory?

Every object, closure, or string lives on the V8 heap. A generational garbage collector (Scavenger + Mark-Sweep-Compact) reclaims it automatically. Much of the work is incremental, concurrent or parallel, but some pauses remain, and when they happen is decided by the collector, not your code.

Zig Systems Model

How does Zig manage memory?

By convention, enforced across the standard library, a function that allocates heap memory takes an explicit allocator: std.mem.Allocator. If a function has no allocator parameter, it normally does not allocate. This is a convention, not a language guarantee: code can still reach std.heap.page_allocator or c_allocator as globals.

What is std.mem.Allocator?

In Zig, an allocator is not a heavyweight C++ virtual class or an invisible runtime global. It is a small interface struct of two words (16 bytes on 64-bit targets): a pointer to the allocator's state and a pointer to a table of functions.

pub const Allocator = struct {
    ptr: *anyopaque,
    vtable: *const VTable,
    // 0.14 VTable: alloc, resize, remap, free (0.13: alloc, resize, free)
};

Because every allocator implements the same interface, you can swap one for another without changing the code that uses it. The 0.14 vtable has alloc, resize, remap, and free (0.13: alloc, resize, free).

How does V8's generational garbage collector work?

V8 splits its heap by object age, based on the observation that most objects die young. Short-lived objects are cleaned up cheaply and often; only survivors pay for the more expensive old-space collection.

New space: the semi-space Scavenger

New space is small and divided into two semi-spaces. Allocation bumps a pointer in the active semi-space. When it fills up, the Scavenger copies the live objects into the other semi-space and discards everything left behind. The cost scales with the number of survivors, not with the amount of garbage. In modern V8 the Scavenger runs in parallel across helper threads, but it still pauses JavaScript while it runs.

Promotion to old space

An object that survives scavenges is promoted into old space. Long-lived data (caches, module state, large arrays) ends up there. A leak in Node usually means objects stay reachable (a growing Map, an unremoved listener), so they are promoted and never collected.

Old space: Mark-Sweep-Compact and Orinoco

Old space uses a major GC: mark reachable objects, sweep dead ones, and sometimes compact to reduce fragmentation. V8's Orinoco project made much of this work incremental (in small slices between JavaScript tasks) and concurrent (on background threads while JavaScript keeps running). Sweeping is also concurrent. As a result, pauses are much shorter than a classic stop-the-world collector, but they still exist: parts of marking start and finish on the main thread, and compaction can pause it. You do not control when they happen, and their length depends on heap size and object graph shape, so measure rather than assume a number.

How do you observe and tune it?

Use node --trace-gc to see each collection, process.memoryUsage() for heap totals, and --max-old-space-size (megabytes) to raise or lower the old-space limit. A bigger limit delays an out-of-memory crash but does not remove collections.

gc_flags.sh Shell 
# Print one line per GC event (Scavenge = young, Mark-Compact = old)
node --trace-gc server.js

# Raise the old-space limit (value in MB)
node --max-old-space-size=4096 server.js

# Heap totals from inside a process
node -e "console.log(process.memoryUsage())"

Which allocators does Zig provide?

Zig ships several allocators in std.heap. You choose one at the program root and pass it down.

DebugAllocator: leak and use-after-free detection

In Zig 0.14, GeneralPurposeAllocator was renamed std.heap.DebugAllocator; the old name remains as a deprecated alias in 0.14, and 0.13 only has GeneralPurposeAllocator. In Debug and ReleaseSafe it tracks leaks, and deinit() returns .ok or .leak; Debug builds add allocation stack traces. Use it as the root allocator while developing:

debug_allocator_example.zig Zig 
const std = @import("std");

pub fn main() !void {
    var debug_allocator = std.heap.DebugAllocator(.{}){};
    defer {
        const status = debug_allocator.deinit();
        if (status == .leak) std.debug.print("memory leak detected\n", .{});
    }
    const allocator = debug_allocator.allocator();

    const numbers = try allocator.alloc(i32, 5);
    defer allocator.free(numbers); // pair every alloc with a defer free

    for (numbers, 0..) |*val, idx| {
        val.* = @intCast(idx * 10);
    }
    std.debug.print("Allocated: {any}\n", .{numbers});
}

ArenaAllocator: free everything at once

An arena wraps a child allocator. Allocations are cheap and rarely need individual free(): freeing a single allocation is a no-op except for the most recent one. deinit() (or reset()) releases everything at once, which fits request handlers and CLI commands. Forgetting deinit() still leaks the whole arena.

arena_example.zig Zig 
const std = @import("std");

fn handleRequest(root_allocator: std.mem.Allocator) !void {
    var arena = std.heap.ArenaAllocator.init(root_allocator);
    defer arena.deinit(); // releases everything the arena obtained from root_allocator
    const req_allocator = arena.allocator();

    var list = std.ArrayList([]const u8).init(req_allocator);
    var i: usize = 0;
    while (i < 100) : (i += 1) {
        const item = try std.fmt.allocPrint(req_allocator, "User session #{d}", .{i});
        try list.append(item);
    }

    std.debug.print("Processed {d} items with no individual frees\n", .{list.items.len});
}

pub fn main() !void {
    var debug_allocator = std.heap.DebugAllocator(.{}){};
    defer _ = debug_allocator.deinit();
    try handleRequest(debug_allocator.allocator());
}

FixedBufferAllocator: allocate from a buffer you provide

FixedBufferAllocator hands out memory from a caller-provided buffer, often on the stack. It makes no syscalls and fails with error.OutOfMemory when the buffer is full, which makes memory use bounded and predictable. That suits embedded code and latency-sensitive paths.

fixed_buffer_example.zig Zig 
const std = @import("std");

pub fn main() !void {
    // 64 KB reserved on the stack; no heap involved
    var stack_buffer: [64 * 1024]u8 = undefined;
    var fba = std.heap.FixedBufferAllocator.init(&stack_buffer);
    const allocator = fba.allocator();

    // Served from stack_buffer, so no syscalls. Returns error.OutOfMemory when full.
    const text = try std.fmt.allocPrint(allocator, "formatted on the stack: {d}", .{42});
    std.debug.print("{s}\n", .{text});
}

page_allocator, c_allocator and smp_allocator

These are the lower-level options. Most programs use one of them (or a debug allocator) as the root and layer arenas on top.

global_allocators.zig Zig 
const std = @import("std");

// Whole pages from the OS (mmap / VirtualAlloc) on every call: wasteful for small objects.
const pages = std.heap.page_allocator;

// Wraps libc malloc/free. Requires linking libc (exe.linkLibC()).
const libc = std.heap.c_allocator;

// Zig 0.14+: fast multithreaded general-purpose allocator, meant for ReleaseFast builds.
const fast = std.heap.smp_allocator;
