Appendix 10 • Diagnostics & Debugging

Diagnostics & Debugging Playbook

Diagnose compile-time errors, runtime panics and memory leaks, and debug native binaries with LLDB.

Direct Answer

Most Zig errors a Node.js developer hits fall into three groups: compile errors from strict types (expected type 'u32', found 'i32', unused locals, ignored error unions), safety panics in Debug and ReleaseSafe builds (index out of bounds, integer overflow), and leaks reported by std.heap.DebugAllocator at deinit(). Read the message, then apply the cause and fix listed below. LLDB or GDB works on Zig binaries because Debug builds include DWARF symbols.

What compile-time errors will I see first?

error: expected type 'u32', found 'i32'

Cause: Zig never converts between integer types implicitly when the value might not fit. JavaScript's single number type hides this. Fix: convert explicitly; @intCast checks the value in safe builds.

const signed: i32 = 42;
const unsigned: u32 = @intCast(signed); // panics in safe builds if signed is negative

error: unused local constant

Cause: the compiler rejects declared but unused locals, and the same applies to unused function parameters. Fix: delete it, use it, or discard it explicitly with _ = name; while prototyping.

const unused = 10;
_ = unused; // explicit discard; remove both lines once the code is finished

error: error union is ignored

Cause: you called a function returning !T and dropped the result, like an un-awaited rejected promise. Zig forces every error to be handled. Fix: propagate with try, handle with catch, or consciously ignore it with catch {} (for !void). A similar message, value of type 'T' ignored, appears for non-error results you drop.

try file.writeAll(data);                          // propagate to the caller
file.writeAll(data) catch |err| log.warn("{s}", .{@errorName(err)}); // handle here

error: dependency on libc must be explicitly specified in the build command

Cause: your code uses std.heap.c_allocator or other libc functions, but the build does not link libc. Fix: link it in build.zig (or pass -lc on the command line).

C import failed: libc headers not available

Cause: @cImport of a libc header (such as stdio.h) without linking libc. Fix: call exe.linkLibC() in build.zig (or pass -lc on the command line).

exe.linkLibC();

What runtime panics should I expect?

Zig panics print a message and a stack trace. These checks are active in Debug and ReleaseSafe. In ReleaseFast and ReleaseSmall they are removed, and violating them is undefined behavior, so test with a safe mode.

panic: index out of bounds: index 5, len 3

Cause: slices and arrays are bounds-checked; JavaScript would return undefined. Fix: check the length first or use if (i < items.len); the stack trace points at the offending line.

panic: integer overflow

Cause: +, -, * on fixed-width integers are checked in Debug and ReleaseSafe; JavaScript silently switches to floating point. Fix: pick a wider type, use wrapping operators (+%) when wraparound is intended, or detect it with std.math.add, which returns error.Overflow.

var counter: u8 = 255;
counter +%= 1;                                  // wraps to 0 on purpose
const sum = try std.math.add(u8, 200, 100); // error.Overflow instead of a panic

panic: attempt to use null value

Cause: you unwrapped an optional with .? that was null, the closest thing to Cannot read properties of undefined. Fix: use orelse or if (opt) |value| { ... }.

How do I detect memory leaks with DebugAllocator?

Leak reports at deinit()

In Debug and ReleaseSafe builds, std.heap.DebugAllocator (named GeneralPurposeAllocator in 0.13, still available as a deprecated alias in 0.14) tracks leaks and reports every allocation that was not freed before deinit(), which returns .ok or .leak; Debug builds add allocation stack traces. The log lines look like memory address 0x... leaked: followed by the allocating stack trace. Fix: find the allocation site in the trace and add the missing defer allocator.free(...) or deinit(). Inside tests, std.testing.allocator fails the test automatically on a leak.

const std = @import("std");

pub fn main() !void {
    // 0.14; on 0.13 use: var gpa = std.heap.GeneralPurposeAllocator(.{}){};
    var debug_allocator: std.heap.DebugAllocator(.{}) = .init;
    defer {
        const check = debug_allocator.deinit();
        if (check == .leak) @panic("Memory leak detected!");
    }
    const allocator = debug_allocator.allocator();

    const buf = try allocator.alloc(u8, 64);
    defer allocator.free(buf); // remove this line to see the leak report
}

How do I set breakpoints with LLDB or GDB?

Native debugging

Zig binaries compile with DWARF debug information by default in Debug mode (-Doptimize=Debug). Step through your code directly in the terminal:

# Build with debug symbols
zig build

# Launch debugger
lldb ./zig-out/bin/my_app
(lldb) breakpoint set --file main.zig --line 25
(lldb) run
(lldb) frame variable
