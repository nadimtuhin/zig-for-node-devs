Appendix 08 • Philosophy & Principles

The Zen of Zig

Created by Andrew Kelley, Zig is designed around explicitness, predictability, and readability.

Direct Answer

The Zen of Zig is the list of principles printed by the zig zen command, such as "Communicate intent precisely", "Edge cases matter", and "Resource allocation may fail; resource deallocation must succeed". In practice it means no operator overloading, no exceptions, no preprocessor macros, and no hidden memory allocation: allocation happens where a function receives and uses a std.mem.Allocator. For Node.js developers, that trades JavaScript's implicit behavior for code whose cost and failure paths are visible.

What Did Zig Deliberately Leave Out, and Why?

  • No operator overloading: In C++ or Python, a + b may invoke an arbitrary user-defined method. In Zig, + only applies to built-in numeric, vector, and pointer types and never calls a user-defined function.
  • No hidden control flow: There are no exceptions and no property getters that run code. Calls look like f(), and early exits are visible as try, catch, return, defer, and errdefer.
  • No hidden memory allocation: By convention, enforced across the standard library, a function that does not take an allocator does not allocate heap memory. It is a convention rather than a compiler guarantee, because code can still reach std.heap.page_allocator or std.heap.c_allocator globally.
  • No preprocessor macros: Zig has no text-substitution macros. Generics, conditional compilation (if on comptime values), and constants are written with comptime and plain Zig code, which the compiler type-checks.

What Does zig zen Print?

This is the text from Zig 0.14. Newer compilers reword a few lines (for example, "Only one obvious way to do things" later became "There is an idiomatic way to do it"), so run zig zen to see your version.

* Communicate intent precisely.
* Edge cases matter.
* Favor reading code over writing code.
* Only one obvious way to do things.
* Runtime crashes are better than bugs.
* Compile errors are better than runtime crashes.
* Incremental improvements.
* Avoid local maximums.
* Reduce the amount one must remember.
* Focus on code rather than style.
* Resource allocation may fail; resource deallocation must succeed.
* Memory is a resource.
* Together we serve the users.

What Does Each Zen Line Mean for a Node.js Developer?

Clarity and readability

  • Communicate intent precisely. Types are explicit (u8, []const u8, ?*Node), so a signature shows whether a value can be null, mutated, or fail. Compare a JS function that accepts "anything".
  • Favor reading code over writing code. Zig accepts more keystrokes (explicit allocators, explicit try) so that a reviewer can see allocation and failure points without running the program.
  • Only one obvious way to do things. Where JavaScript offers for, forEach, for...of and map, Zig keeps a small set of constructs. Expect less syntactic variety and more uniform code.
  • Reduce the amount one must remember. No lossy implicit conversions, no operator overloading, and no macros mean fewer rules to carry in your head while reading someone else's code.
  • Focus on code rather than style. zig fmt is built into the toolchain, so there is no Prettier-versus-ESLint configuration debate.

Correctness and failure

  • Edge cases matter. Integer overflow, out-of-memory, and empty slices are part of normal design. Every allocator.alloc returns an error union because allocation can fail, unlike new Array(n) in JS.
  • Runtime crashes are better than bugs. In Debug and ReleaseSafe builds, bounds violations and integer overflow panic loudly instead of silently corrupting data. This is the safety you give up in ReleaseFast, so choose build modes on purpose.
  • Compile errors are better than runtime crashes. Unused variables, ignored error returns, and non-exhaustive switch statements are rejected at build time, which TypeScript only catches with noUnusedLocals, a never check, or a lint rule.

Memory and resources

  • Resource allocation may fail; resource deallocation must succeed. Allocation returns error.OutOfMemory, while allocator.free returns nothing, so it can go in a defer on every path.
  • Memory is a resource. The heap is not an invisible runtime service as it is under V8's garbage collector. It is something you acquire from an allocator and release, like a file handle.

Process and community

  • Incremental improvements. Zig is pre-1.0, and standard library APIs change between releases (for example, GeneralPurposeAllocator became DebugAllocator in 0.14). Pin your compiler version and read the release notes before upgrading.
  • Avoid local maximums. The project prefers a better long-term design over a quick fix that would be hard to undo, even when that means breaking changes.
  • Together we serve the users. Decisions are meant to benefit the people who use the software, not just the people who write the compiler.
