Appendix 01 • Metaprogramming Paradigm

Mastering Zig comptime

How Zig replaces C preprocessor macros, C++ templates, and much runtime reflection with ordinary Zig code that the compiler executes at build time.

Direct Answer

Zig comptime runs ordinary Zig code inside the compiler, so a generic is a plain function that takes comptime T: type and returns a type, and @typeInfo(T) lets you inspect fields and tags during compilation. TypeScript types are erased by tsc or esbuild before your code runs: they cannot execute code or exist at runtime. Comptime code cannot do I/O, and loops are limited by @setEvalBranchQuota (default 1000 backward branches).

What is comptime, and how is it different from TypeScript types?

TypeScript types are erased when tsc or esbuild strips them, so nothing remains at runtime. To inspect objects in Node.js you use runtime reflection (Object.keys(), Reflect.get(), libraries such as class-transformer). TypeScript's type system is Turing-complete (recursive conditional and template literal types can compute), but it only computes other types: it cannot run arbitrary code, do I/O, or produce runtime values.

In Zig, types are first-class values at compile time. You write ordinary Zig functions, loops, and switches. When an expression is marked comptime, the compiler executes it during compilation and can produce values, types and code from the result. Comptime code cannot perform I/O or syscalls, and it stays within an evaluation budget.

What does a TypeScript generic look like next to a Zig generic?

Same idea, different mechanism. TypeScript generics are annotations the checker validates and then discards. Zig generics are functions that run at compile time, and the compiler specialises code for each type you pass.

generics.ts TypeScript 
function first<T>(xs: T[]): T | undefined {
  return xs[0];
}

// A type-level "function" (erased at compile time)
type Box<T> = { value: T };

// After tsc/esbuild, the output is plain JS:
// function first(xs) { return xs[0]; }
// Box and T no longer exist at runtime.
generics.zig Zig 
fn first(comptime T: type, xs: []const T) ?T {
    if (xs.len == 0) return null;
    return xs[0];
}

// A type-level function is just a function returning `type`
fn Box(comptime T: type) type {
    return struct { value: T };
}

// first(i32, ...) and first(f64, ...) compile to separate
// specialised functions. Box(i32) is a real type.

How do generics work without new syntax?

A generic data structure is a regular function that takes a comptime T: type parameter and returns a type. You can reject unsupported types with @compileError, which fails the build with your message. The tag names below (.int, .float) are Zig 0.14 spelling; in 0.13 write .Int and .Float.

generic_point.zig Zig 
const std = @import("std");

pub fn Point(comptime T: type) type {
    // Assert at compile time that T is either an integer or float
    comptime {
        const info = @typeInfo(T);
        if (info != .int and info != .float) {
            @compileError("Point(T) only supports integer or float types!");
        }
    }

    return struct {
        x: T,
        y: T,

        const Self = @This();

        pub fn distance(self: Self) f64 {
            const x_f64: f64 = switch (@typeInfo(T)) {
                .int => @floatFromInt(self.x),
                .float => @floatCast(self.x),
                else => unreachable,
            };
            const y_f64: f64 = switch (@typeInfo(T)) {
                .int => @floatFromInt(self.y),
                .float => @floatCast(self.y),
                else => unreachable,
            };
            return @sqrt(x_f64 * x_f64 + y_f64 * y_f64);
        }
    };
}

pub fn main() void {
    const PointI32 = Point(i32);
    const pt1 = PointI32{ .x = 3, .y = 4 };
    std.debug.print("Distance: {d}\n", .{pt1.distance()}); // 5

    const PointF32 = Point(f32);
    const pt2 = PointF32{ .x = 1.5, .y = 2.0 };
    std.debug.print("Distance: {d}\n", .{pt2.distance()}); // 2.5
}

How do you inspect types with @typeInfo, and what changed in 0.14?

@typeInfo(T) returns a std.builtin.Type tagged union that describes T. Zig 0.14 changed the tag names to lowercase (using @"..." quoting where the name is a keyword), while 0.13 used capitalised tags. Code written for one version fails to compile on the other:

KindZig 0.14 tagZig 0.13 tag
Struct .@"struct" .Struct
Integer / float .int, .float .Int, .Float
Pointer / array .pointer, .array .Pointer, .Array
Enum / union / fn .@"enum", .@"union", .@"fn" .Enum, .Union, .Fn
typeinfo_tags.zig Zig 
const std = @import("std");

fn describe(comptime T: type) []const u8 {
    return switch (@typeInfo(T)) {
        // Zig 0.14 tag names. In 0.13 these are .Int, .Float, .Struct
        .int => "integer",
        .float => "float",
        .@"struct" => "struct",
        else => "something else",
    };
}

const Pair = struct { a: i32, b: i32 };

pub fn main() void {
    std.debug.print("{s} {s} {s}\n", .{
        describe(u8), describe(f32), describe(Pair),
    });
    // std.meta.fields(Pair) is a shortcut for the struct field list
    inline for (std.meta.fields(Pair)) |fld| {
        std.debug.print("field: {s}\n", .{fld.name});
    }
}

How does inline for enable compile-time reflection?

A regular for loop executes at runtime. An inline for loop is unrolled by the compiler, which lets you write a serializer that visits each struct field without a runtime lookup of field names. The field list is known when the code is compiled, so there is no runtime reflection step. This version uses 0.14 tag names (in 0.13 the prong is .Struct):

serializer.zig Zig 
const std = @import("std");

pub fn printStructFields(comptime T: type, value: T) void {
    const info = @typeInfo(T);
    switch (info) {
        .@"struct" => |s| {
            std.debug.print("Inspecting struct {s}:\n", .{@typeName(T)});
            inline for (s.fields) |field| {
                const val = @field(value, field.name);
                std.debug.print("  - {s} ({s}) = {any}\n", .{
                    field.name,
                    @typeName(field.type),
                    val,
                });
            }
        },
        else => @compileError("printStructFields requires a struct type!"),
    }
}

const UserAccount = struct {
    id: u64,
    name: []const u8,
    active: bool,
};

pub fn main() void {
    const user = UserAccount{ .id = 42, .name = "Alice", .active = true };
    printStructFields(UserAccount, user);
}

What can comptime precompute, and what are its limits?

You can compute values at build time and use them as constants, for example FNV-1a hashes of route strings used as switch cases instead of comparing strings with std.mem.eql in sequence. Different strings can in principle share a hash, so this is a dispatch technique to measure, not a proven win.

comptime_router.zig Zig 
const std = @import("std");

pub fn hashString(s: []const u8) u64 {
    var h: u64 = 0xcbf29ce484222325;
    for (s) |b| {
        h = (h ^ b) *% 0x100000001b3;
    }
    return h;
}

pub fn route(path: []const u8) []const u8 {
    // The comptime prong items are evaluated by the compiler, not at runtime
    switch (hashString(path)) {
        comptime hashString("/health") => return "200 OK: Healthy",
        comptime hashString("/api/v1/users") => return "200 OK: Users List",
        comptime hashString("/api/v1/orders") => return "200 OK: Orders List",
        else => return "404 Not Found",
    }
}

pub fn main() void {
    std.debug.print("Route result: {s}\n", .{route("/health")});
}

What limits does comptime have?

Comptime code cannot perform I/O or syscalls (no reading files or the network; use @embedFile to bring a file's bytes in). Evaluation is bounded: the compiler stops a loop after 1000 backward branches by default, and you raise the limit with @setEvalBranchQuota. Heavy comptime work also slows the build.

quota.zig Zig 
const std = @import("std");

fn sumTo(comptime n: u32) u32 {
    @setEvalBranchQuota(100_000); // default is 1000 backward branches
    var total: u32 = 0;
    var i: u32 = 0;
    while (i < n) : (i += 1) total += i;
    return total;
}

pub fn main() void {
    const result = comptime sumTo(5000); // computed during compilation
    std.debug.print("{d}\n", .{result});
}
