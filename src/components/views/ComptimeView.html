Appendix 01 • Metaprogramming Paradigm

Mastering Zig `comptime`

Why Zig eliminates C preprocessor macros, C++ template errors, and JavaScript runtime reflection in favor of ordinary Zig code executed at compile time.

⚡ What is `comptime`?

In JavaScript, generics are stripped by TypeScript, and dynamic reflection requires runtime inspection (Object.keys, Reflect.get, eval()). In C++, templates create cryptic error messages and bloated compile times.

In Zig, types are first-class values at compile time. You write regular Zig syntax (loops, branches, function calls), and if a parameter is marked comptime, the Zig compiler executes that code inside the compiler VM during compilation.

1. Type Generics without New Syntax

// Zig generics are just functions returning a struct type!
fn Point(comptime T: type) type {
    return struct {
        x: T,
        y: T,
        
        pub fn distance(self: @This()) f64 {
            const dx = @as(f64, @floatFromInt(self.x));
            const dy = @as(f64, @floatFromInt(self.y));
            return @sqrt(dx * dx + dy * dy);
        }
    };
}

pub fn main() void {
    const PointI32 = Point(i32);
    const pt = PointI32{ .x = 3, .y = 4 };
    _ = pt;
}

2. Comptime Reflection with `@typeInfo`

// Inspect struct fields at compile time to build zero-allocation serializers!
fn printFields(comptime T: type) void {
    const info = @typeInfo(T);
    switch (info) {
        .@"struct" => |s| {
            inline for (s.fields) |field| {
                std.debug.print("Field: {s} (type: {s})\n", .{
                    field.name, @typeName(field.type)
                });
            }
        },
        else => @compileError("T must be a struct!"),
    }
}
Pro Tip for Node.js Devs:

Notice inline for! A regular for loop iterates at runtime. An inline for instructs the compiler to unroll the loop completely at compile time, creating bespoke, branchless machine code for every field.
