Appendix 06 • Container Architecture

Production Docker Recipes: Static Zig Binaries on Scratch

How a statically linked Zig binary lets you ship a container with no OS layer, no package manager and no Node runtime, and what you give up when you do.

Direct Answer

To containerize a Zig service, build it in a multi-stage Dockerfile with zig build -Dtarget=x86_64-linux-musl -Doptimize=ReleaseSafe -Dcpu=baseline, then copy the resulting static ELF into a FROM scratch image and run it as USER 65534. The image is then roughly the size of the binary, because there is no Node runtime, shell or OS package set to ship. Measure the result with docker images and ls -l zig-out/bin.

What does a multi-stage Zig Dockerfile look like?

The build stage downloads a pinned Zig release and compiles for x86_64-linux-musl. musl links statically, so the output has no dependency on a system libc and can run on an empty filesystem. For ARM hosts, swap in aarch64 in the tarball name and the -Dtarget value.

Production Multi-Stage Dockerfile (Static Scratch Build) 
# Stage 1: build the static Zig binary
FROM alpine:3.20 AS build

ARG ZIG_VERSION=0.14.0

# curl + xz to unpack the compiler; ca-certificates is copied into the final image later
RUN apk add --no-cache curl xz ca-certificates

# Tarball naming changed in 0.14.1: zig-x86_64-linux-<ver>.tar.xz (0.14.0 used zig-linux-x86_64-<ver>). Adjust if you bump ZIG_VERSION.
# Official tarball from ziglang.org/download (pin the version, verify the checksum for real pipelines)
RUN curl -fsSL https://ziglang.org/download/${ZIG_VERSION}/zig-linux-x86_64-${ZIG_VERSION}.tar.xz \
      | tar -xJ -C /opt \
    && ln -s /opt/zig-linux-x86_64-${ZIG_VERSION}/zig /usr/local/bin/zig

WORKDIR /src
COPY . .

# Static musl binary; -Dcpu=baseline avoids CPU-specific instructions so it runs on any x86_64 host.
# ReleaseSafe keeps bounds/overflow checks; ReleaseSmall minimises size (both are reasonable for services).
RUN zig build -Dtarget=x86_64-linux-musl -Doptimize=ReleaseSafe -Dcpu=baseline

# Stage 2: empty filesystem
FROM scratch

# CA bundle, only needed for outbound TLS (HTTPS APIs, databases with TLS)
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/ca-certificates.crt
COPY --from=build /src/zig-out/bin/server /server

EXPOSE 8080
# Numeric UID: scratch has no /etc/passwd, so a user name would not resolve
USER 65534:65534

# Exec form so the server is PID 1 and receives SIGTERM directly; PID 1 ignores SIGTERM unless the program installs a handler
ENTRYPOINT ["/server"]

Your build.zig must expose the target and optimize options for those flags to work: b.standardTargetOptions(.{}) and b.standardOptimizeOption(.{}). If you install the executable under a different name, adjust the COPY path.

How big is a Zig scratch image compared to Node.js images?

Official Node image sizes vary by tag and over time, so treat these as rough orders of magnitude and check your own tags. The Zig row is not a fixed number: it is whatever your binary weighs.

Base image Roughly (uncompressed) What is inside
node:22 (Debian bookworm) ~1.1 GB Full Debian userland, compilers, Node, npm, yarn
node:22-slim ~200 MB Minimal Debian, Node, npm
node:22-alpine ~150-160 MB Alpine (musl, busybox), Node, npm
Distroless Node Smaller than slim; check the tag No shell or package manager, but still ships the Node runtime plus your node_modules
Zig on scratch About the size of the binary. Typically KBs for small tools and low single-digit MB for HTTP services. Measure it. One static ELF (plus the CA bundle if you copied it)

Measure your own build instead of trusting any table:

docker build -t my-zig-svc .
docker images my-zig-svc
ls -l zig-out/bin/server
file zig-out/bin/server   # expect: statically linked

Does a scratch image really have zero CVEs?

The precise claim is narrower: an image scanner finds no OS packages to flag, because there are none. That removes the largest source of scanner noise (glibc, OpenSSL, busybox, apt and friends), but it does not make the service vulnerable-free.

  • Bugs in your own Zig code, including logic and authorization flaws, are still yours.
  • Vendored C libraries (SQLite, zlib, an HTTP parser) are compiled into the binary, and scanners often cannot see them. Track their versions yourself.
  • Zig dependencies from build.zig.zon have no central advisory database, so review updates manually.
  • The Zig compiler and the build stage are not in the final image, but they still deserve patching in CI.

What breaks on FROM scratch?

No shell

docker exec -it c sh fails, and so do shell-form CMD and HEALTHCHECK CMD curl .... Use exec-form entrypoints, and give the binary its own health subcommand (for example /server --healthcheck) or probe from the orchestrator over HTTP.

No CA certificates

Outbound HTTPS fails certificate verification unless you copy /etc/ssl/certs/ca-certificates.crt from the build stage, as in the Dockerfile above.

No timezone database and no /etc/passwd

There is no /usr/share/zoneinfo, so local-time conversion needs data copied in or, better, keep everything in UTC. Use a numeric USER 65534; user names do not resolve without /etc/passwd.

No writable temp directory

There is no /tmp unless you create it. Mount a volume or tmpfs if the service writes files.

How do I debug it?

  • Build a second target with FROM alpine and the same binary when you need a shell, then compare behavior.
  • Attach an ephemeral debugger container sharing the process namespace: docker run --rm -it --pid=container:NAME --net=container:NAME alpine sh (Kubernetes: kubectl debug).
  • Log to stderr and let the platform collect it; there is no file system to inspect.
  • Reproduce crashes in Debug mode locally, where Zig prints a stack trace and DebugAllocator reports leaks.

Which optimize mode and CPU target should I ship?

  • ReleaseSafe: optimizations on, bounds checks and integer-overflow checks kept. A good default for network services.
  • ReleaseSmall: smallest binary; safety checks are removed.
  • ReleaseFast: fastest; safety checks are removed, so violations are undefined behavior.
  • -Dcpu=baseline: generic CPU features so the image runs on any host of that architecture. A native build that uses the build machine's newer instructions can crash with SIGILL on older hosts; being explicit documents intent.
