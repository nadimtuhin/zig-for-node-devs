Appendix 09 • Guardrails

Top 8 Known Pitfalls & Footguns

Where JavaScript and Node.js intuition leads to bugs in systems programming.

Direct Answer

The most common Zig mistakes for Node.js developers all come from the missing garbage collector: returning a slice of a stack array, forgetting defer allocator.free(...), and keeping slices after arena.deinit(). Zig also has no implicit safety nets that JavaScript hides, so undefined memory, UTF-8 byte lengths, and integer overflow in ReleaseFast builds need deliberate handling. std.testing.allocator and the Debug and ReleaseSafe build modes catch most of them.

1. Returning a Slice of a Local Stack Array

In Node.js, returning an array from a function is safe because the garbage collector keeps it alive while it is reachable. In Zig, a slice or pointer into a local array dangles once the stack frame unwinds (Zig 0.14 compiles this without complaint). Allocate from a caller-passed allocator when returning dynamically sized data, and document that the caller owns the result.

fn greetBad() []const u8 {
    var buf: [16]u8 = undefined;
    return buf[0..4]; // dangling: buf dies when greetBad returns
}

fn greetGood(allocator: std.mem.Allocator) ![]u8 {
    return allocator.dupe(u8, "ping"); // caller must free
}

2. Reading undefined Memory

In JS, undefined is a concrete value of its own type. In Zig, var x: i32 = undefined; means the variable holds no meaningful value yet, and reading it before writing is illegal behavior. Debug builds fill the memory with a recognizable 0xaa byte pattern to help you spot it, but you cannot rely on a panic. Use undefined only for buffers you are about to fill, and give everything else a real initial value.

3. Forgetting defer allocator.free(slice)

Because there is no garbage collector, every heap allocation leaks unless it is paired with free or deinit, or owned by an arena that is itself deinitialized. Put the defer on the line right after the allocation. std.testing.allocator fails a test when something is left allocated, and in a real program std.heap.DebugAllocator (GeneralPurposeAllocator before 0.14) reports leaks when you call deinit().

test "buffer is freed" {
    const allocator = std.testing.allocator;
    const buf = try allocator.alloc(u8, 64);
    defer allocator.free(buf); // delete this line and the test fails with a leak report
}

4. Modifying Function Parameters Directly

Function parameters in Zig are immutable. Writing param = new_value; is a compile error. Make an explicit local copy with var local = param;, or pass a mutable pointer *T when the caller should see the change.

5. Assuming Slices Outlive Short-Lived Allocators

Slices that point into an ArenaAllocator or a temporary buffer become invalid the instant arena.deinit() (or reset()) runs. If a response or long-lived cache needs the data, duplicate the bytes with the persistent allocator before tearing down the arena.

var arena = std.heap.ArenaAllocator.init(gpa);
defer arena.deinit();

const scratch = try arena.allocator().dupe(u8, "temporary");
const keep = try gpa.dupe(u8, scratch); // survives arena.deinit(); free it yourself

6. Silently Swallowing Errors with catch {}

In JavaScript, an unhandled error crashes the process or fires unhandledRejection. In Zig, calling an error-returning function and ignoring the result (doWork();) is a compile error, and so is _ = doWork(); (error union is discarded), which is good. The footgun is the escape hatch: doWork() catch {}; compiles and silently swallows the error. Reserve it for cases where failure truly does not matter, and log or propagate everywhere else.

doWork();        // compile error: error union is ignored
_ = doWork();     // compile error: error union is discarded
doWork() catch {};     // compiles: error silently thrown away
doWork() catch |err| std.log.err("doWork failed: {s}", .{@errorName(err)});

7. Confusing UTF-8 Byte Length with Character Count

In JavaScript, "⚡".length is 1 because length counts UTF-16 code units (and an emoji outside the BMP such as 😀 reports 2). In Zig, "⚡".len is 3 because strings are plain UTF-8 byte slices. Never slice at arbitrary byte offsets when the text may contain multi-byte characters. Iterate code points with std.unicode.Utf8View (std.unicode.Utf8View.init(s) then .iterator()) instead.

8. Integer Overflow in Production (ReleaseFast vs ReleaseSafe)

In Debug and ReleaseSafe, integer arithmetic like a + b panics on overflow. In ReleaseFast and ReleaseSmall, safety checks are removed and overflow is undefined behavior, so you cannot assume it wraps. If wrapping is intentional, use the explicit wrapping operators +%, -%, *%; to detect overflow, use builtins such as @addWithOverflow.

fn wrappingAdd(a: u8, b: u8) u8 {
    return a +% b; // 250 +% 10 == 4 in every build mode
}

How Do I Catch These Pitfalls Before Production?

Test with std.testing.allocator

Run zig test or zig build test. Leaks and double frees on testing-allocator memory fail the test with a report (pitfall 3). Use-after-free is not reliably caught, so do not count on tests to find it.

Ship ReleaseSafe unless you have measured a need for ReleaseFast

ReleaseSafe keeps overflow and bounds checks (pitfall 8) while still optimizing. Switch to -Doptimize=ReleaseFast only after profiling shows the checks matter.

Use DebugAllocator in development

Its deinit() returns .leak when memory was not freed, so you can assert on it at program exit. In 0.14 it replaces GeneralPurposeAllocator, which remains as a deprecated alias.
