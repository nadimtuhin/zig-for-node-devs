Appendix 05 • Production Architecture

Real-World Microservice Architecture: Express.js vs Zig

Re-architecting a standard Express.js REST microservice with Zig's std.http.Server, per-request arenas, a thread pool and signal-based shutdown.

Direct Answer

A Zig microservice replaces Express with std.http.Server: you bind with std.net.Address.listen, call accept(), read headers with receiveHead() and answer with request.respond(). Each request gets its own std.heap.ArenaAllocator that is freed in one deinit(), and concurrency is added explicitly with std.Thread.Pool. There is no garbage collector, so no GC pauses; tail latency depends on your code and the OS scheduler.

How does a Zig request lifecycle compare to Express or Fastify?

Stage Express / Fastify Zig std.http.Server
Accept libuv accepts; the http module's parser emits a req object You call server.accept() and receiveHead() yourself
Routing Router and middleware stack (app.use); Fastify uses a radix-tree router and hooks A switch or std.mem.eql on request.head.method and request.head.target
Memory Objects allocated on the V8 heap and reclaimed by the garbage collector at times V8 chooses Arena per request; everything freed at one known point when the handler returns
Concurrency One event-loop thread; async I/O; CPU work blocks everything unless moved to worker threads Blocking calls; you choose threads (std.Thread.Pool) or a library with an event loop
Errors Thrown exceptions and rejected promises, caught by error middleware Error unions: try or catch, and you decide the HTTP status

This guide does not quote latency or throughput figures: they depend on payload, hardware, kernel settings and your handlers. Benchmark your own workload before and after a migration.

How do I write the std.http.Server request loop in Zig 0.14?

The server accepts a TCP connection, wraps it in std.http.Server.init(conn, &read_buffer), then loops on receiveHead() so keep-alive connections serve several requests. Each request builds its response inside an arena, so no handler needs a matching free.

const std = @import("std");
const Allocator = std.mem.Allocator;

const User = struct {
    id: u32,
    username: []const u8,
    email: []const u8,
};

pub fn main() !void {
    // 0.14: DebugAllocator (GeneralPurposeAllocator is a deprecated alias; 0.13 only has the old name).
    // Reports leaks on deinit() in Debug builds; use std.heap.smp_allocator for ReleaseFast.
    var debug_allocator: std.heap.DebugAllocator(.{}) = .init;
    defer _ = debug_allocator.deinit();
    const base = debug_allocator.allocator();

    const address = try std.net.Address.parseIp("0.0.0.0", 8080);
    var server = try address.listen(.{ .reuse_address = true });
    defer server.deinit();

    std.log.info("listening on 0.0.0.0:8080", .{});

    while (true) {
        const conn = try server.accept();
        handleConnection(base, conn) catch |err| {
            std.log.err("connection failed: {s}", .{@errorName(err)});
        };
    }
}

fn handleConnection(base: Allocator, conn: std.net.Server.Connection) !void {
    defer conn.stream.close();

    var read_buffer: [4096]u8 = undefined;
    var http = std.http.Server.init(conn, &read_buffer);

    while (http.state == .ready) {
        var request = http.receiveHead() catch |err| switch (err) {
            error.HttpConnectionClosing => return,
            else => return err,
        };

        // One arena per request: every allocation below is freed by this single deinit()
        var arena = std.heap.ArenaAllocator.init(base);
        defer arena.deinit();

        try route(arena.allocator(), &request);
    }
}

fn route(req_alloc: Allocator, request: *std.http.Server.Request) !void {
    const json_header = std.http.Header{ .name = "content-type", .value = "application/json" };

    if (request.head.method == .GET and std.mem.eql(u8, request.head.target, "/health")) {
        return request.respond("{\"status\":\"ok\"}", .{ .extra_headers = &.{json_header} });
    }

    if (request.head.method == .GET and std.mem.eql(u8, request.head.target, "/api/v1/user")) {
        const user = User{ .id = 101, .username = "nadimtuhin", .email = "nadim@example.com" };
        // 0.14 API; later releases rename the JSON helpers, so check your version's std.json
        const body = try std.json.stringifyAlloc(req_alloc, user, .{});
        return request.respond(body, .{ .extra_headers = &.{json_header} });
    }

    return request.respond("not found", .{ .status = .not_found });
}

Version note: this targets Zig 0.14. The std.http.Server shape (init(conn, &buffer), receiveHead(), request.respond()) is the same since 0.12, but 0.15 rewrote std.http and std.Io, so expect to adapt the connection setup there.

Why use an ArenaAllocator per request?

An arena collects every allocation made while handling one request and releases them all in deinit(). Individual free calls are effectively no-ops (apart from the most recent allocation), so handlers stay simple and cannot leak across requests. It is the closest Zig analogue to "the garbage collector cleans up after the request", except that the cleanup point is explicit and deterministic.

  • Anything that must outlive the request (caches, sessions) has to be allocated from the long-lived base allocator instead, and freed explicitly.
  • For hot paths you can back the arena with std.heap.stackFallback(4096, base).get(), which serves from a stack buffer and falls back to base when it fills.

How do I handle many connections with std.Thread.Pool?

std.http.Server is blocking and handles one connection at a time, so the loop above serves a slow client at the expense of everyone else. The simplest fix is to hand each accepted connection to a std.Thread.Pool.

var pool: std.Thread.Pool = undefined;
try pool.init(.{ .allocator = base, .n_jobs = 8 });
defer pool.deinit();

while (true) {
    const conn = try server.accept();
    try pool.spawn(worker, .{ base, conn });
}

fn worker(base: Allocator, conn: std.net.Server.Connection) void {
    handleConnection(base, conn) catch |err| {
        std.log.err("connection failed: {s}", .{@errorName(err)});
    };
}
  • Pool jobs cannot return errors, so the worker must catch and log them.
  • The allocator is now shared across threads. DebugAllocator is thread-safe in multi-threaded builds; for production prefer std.heap.smp_allocator (0.14+) or std.heap.c_allocator with libc linked.
  • Shared mutable state (counters, caches) needs std.Thread.Mutex or atomics. Nothing makes this safe for you.
  • A pool of N threads still ties up a thread per slow connection. For tens of thousands of idle keep-alive connections, look at libraries with an event loop such as http.zig, or zap, which wraps facil.io.

How do I shut down gracefully on SIGTERM?

Containers receive SIGTERM on stop. A process running as PID 1 gets no default signal action, so a Zig server that never installs a handler will ignore it until Docker force-kills it after the grace period. Install a handler with std.posix.sigaction that sets a std.atomic.Value(bool), check the flag in the accept loop, stop accepting, then call pool.deinit() so worker threads are joined before exit.

  • A blocking accept() will not notice the flag by itself. Use poll with a timeout and check the flag, or call std.posix.shutdown(listen_fd, .recv) from a watcher thread; close() alone won't wake a blocked accept() on Linux.
  • Signal handlers may only do async-signal-safe work: set the atomic flag and return, no allocation or logging.
  • Verify in your Zig version how pool.deinit() treats queued but unstarted jobs; if in-flight requests must finish, track them yourself.
